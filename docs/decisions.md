primary source instead of being taken from memory. Dates are absolute. Newest entries at the bottom of each section.

## Decisions

### D1 – Brand lives in one place
`Ahmedhsieb\RequestTracer\Support\Brand` holds the name, header, gate name, log channel, mask string and storage directory.
Renaming = change `composer.json` `name`, find-and-replace the `Ahmedhsieb\RequestTracer\` namespace, edit `Brand`.
Config file (`config/request-tracer.php`), route prefix (`/request-tracer`), view namespace and cache keys derive from `Brand::NAME`.

### D2 – Extra span types
The brief lists twelve span types. Roots need their own: `request`, `command` (artisan + scheduled task). `job` already exists. They are documented as part of the span model.

### D3 – Decision to record is made early, confirmed late
Watch-list recording needs the authenticated user, which only exists after the session middleware. A request is therefore
either `off`, `tentative` (recorded into memory, kept only if a user matching the watch list or the sampling rules authenticates) or `on`
(signed token, local environment, `always` mode). Tentative requests that never confirm are discarded in `terminate()` with no write. A tentative recording only
happens when the watch list is non-empty or sampling is enabled, so the default production cost of an unrelated request is one header check.

### D4 – Recording default
`mode = null` resolves to `always` in `local_environments` and `triggered` everywhere else (brief: "Recording default on production: OFF").
The dashboard shows the active mode and a `production` badge.

### D5 – Storage payload encoding
Payloads (`input`, `output`, `result`, `before`, `after`) are JSON; when larger than `compress_over_bytes` they are stored as `gz:` + base64(gzip(json))
in a `longText` column. Binary columns were rejected: `bytea` (PostgreSQL) and `varbinary` (SQL Server) need driver-specific parameter binding, text is portable
to all four supported engines.

### D6 – Span identity
`tracer_spans.id` is a per-trace integer; the primary key is `(trace_id, id)`. This keeps `parent_id` valid inside one bulk insert without reading back auto-increment values.

### D7 – Extra columns
Added beyond the brief, all nullable: `tracer_traces.tables_read` (json: table → queries/rows), `tracer_traces.kind` (`request|job|command|schedule`),
`tracer_traces.parent_trace_id` (job → dispatching trace), `tracer_traces.mode`, `tracer_traces.environment`, `tracer_writes.transaction`
(`none|committed|rolled_back|open`), `tracer_writes.rows` (affected row count where known), `tracer_spans.count`/`total_us` for collapsed spans, `tracer_spans.meta`.

### D8 – Row counts for tables that were only read
`QueryExecuted` does not carry a result count. Eloquent `retrieved` events are counted per table (cheap, no span), so the dashboard shows
real row counts for rows hydrated through Eloquent and query counts for everything else. Documented as a limitation.

### D9 – Events
The Laravel event dispatcher offers no before/after-listener hook; replacing the `events` instance is unsafe (the router, DB connections and Eloquent hold the original).
Event spans are recorded from a wildcard listener (which Laravel runs after the specific listeners), together with the introspected list of listeners.
Work done *by* listeners appears as sibling spans just before the event span; listeners that are classes in a proxied namespace get their own `handle` span (layer 2).
Documented in "How capture works".

### D10 – Proxies hook into the container with `beforeResolving`
For a class in a configured namespace the container binding is replaced (keeping the shared flag) by a closure that builds the generated subclass through the container,
so the parent constructor receives its dependencies. Contextual bindings are copied to the proxy class. Classes bound to custom closures, final classes,
and objects created with `new` cannot be proxied; the dashboard says so ("not traceable: final").

### D11 – Deep trace compiles by source edits, not by pretty printing
`nikic/php-parser` is used only to find node positions (`startFilePos`/`endFilePos`); probes are inserted as text edits on the original source.
That keeps every original line, comment and whitespace untouched, so line numbers are identical by construction and the diff is minimal. It works the same with php-parser v4 and v5.

### D12 – No closures in config
`config:cache` cannot serialize closures. Resolvers (tenant, module) and custom storage drivers are class names; closures can be registered from a provider through the `Tracer` facade.

### D13 – "Not run" is only shown on lines that carry a probe
Deep trace stores the probes that were hit, never the ones that were not. Marking every code-looking line without a row as "not run" was wrong for the continuation lines of a multi-line statement.
The span-lines endpoint therefore compiles the function again (read only, nothing is written) and returns the probe lines as `statements`; the dashboard marks only those. If the file cannot be compiled the dashboard falls back to a text heuristic.

### D14 – The dashboard has no router and no UI library
The app is a few screens, so it uses the History API directly (`<base>/trace/<id>`) and a small store. That keeps the committed `dist/` at about 140 KB (51 KB gzip), and the only runtime dependency is Vue.

### D15 – Background work is recorded on the same terms as requests, with different triggers
A request has a header to carry a trigger; a job or command has not. In `triggered` mode a job is recorded when the trace that dispatched it was recorded (the queue payload carries a stamp), and a command or scheduled task when the process has `REQUEST_TRACER=1`. `always` mode records everything not excluded. Scheduled artisan commands run in child processes and are recorded there as commands, so only closures, invokables and `->job()` dispatches become `schedule` traces. A job that runs inside another trace (`sync` queue, `Artisan::call()`) is part of that trace.

### D16 – The queue payload stamp is registered on every boot
`Queue::createPayloadUsing()` callbacks are static. A "registered once per process" flag looks right but breaks when the framework clears the callbacks (its test teardown does). The callback is a static closure that reads the current tracer, so registering it on every boot is harmless; in production the provider boots once per process.

### D17 – Cheap checks first
In `triggered` mode the decision looks for a trigger (header, watch list, sampling) before it evaluates the exclusion patterns, because the common case is "no trigger" and the patterns cost a regular expression each. Excluded paths still win whenever something did trigger.

### D18 – Middleware built by a closure is decorated, not subclassed
Laravel registers `StartSession` with a closure, and a generated subclass cannot be used when a closure decides how the instance is built. For middleware (and only middleware) the binding is wrapped: the closure still builds the object, and a small decorator forwards `handle()` inside a `middleware` step. The decorator defines `terminate()` only when the middleware does (the kernel finds it with `method_exists()`), so terminable middleware keeps working. Services bound to closures are still left alone: wrapping them would break type checks against the class.

### D19 – `created_at` is UTC
Carbon 2 and Carbon 3 disagree about the zone of `createFromTimestamp()`, and the table has no zone column, so the value is always written in UTC, compared in UTC (retention, `from`/`to` filters) and returned as ISO 8601 with its offset. Found by running the dashboard in a real application in another time zone than the browser.

### D20 – The Deep trace autoloader steps aside for what it uses itself
It is registered in front of Composer's, so it is asked for every class. PHP does not re-enter the autoloader for a class that is already being autoloaded, so using such a class from inside the autoloader fails. The loader returns immediately for the package's own and php-parser classes and runs its code once before it is registered, which loads everything else it needs the normal way. A test runs the real order in a PHP process of its own, because the test suite itself has those classes loaded already.

### D21 – "Listening" is a heartbeat file, not a mode switch
`request-tracer:listen` has to switch recording on in *other* processes (PHP-FPM workers, `artisan serve`, queue workers, commands) without a database round trip and without anything to clean up. It touches `storage/framework/request-tracer/listening` every second; everybody else compares that file's modification time with the clock (one `stat()`, a few microseconds) and treats four seconds as fresh. Kill the command and recording stops by itself. The price is that the file is local: the command has to run on the machine whose requests you want to see (documented). The same check decides whether the autoloader compiles code for line-by-line tracing, so requests nobody traces run the original files.

### D22 – Nothing records on its own, local included
The first version recorded every request in the `local` environment. That is the behaviour people end up fighting (a database that fills up, a slower local app, traces nobody asked for). Now `triggered` is the default everywhere, and "local" only decides who may open the dashboard. `always` stays available as an explicit opt-in.

### D23 – The scope is folders, not classes
People think in folders ("trace the billing module"), not in namespaces or class lists, and they want everything traced unless they say otherwise. `code.paths` (default `app`) says what is looked into and `code.except` what is not; both take folders and files, and `except` also takes class patterns. The same rule decides which files are compiled for line-by-line tracing and which classes get a container proxy. Proxies skip what the framework builds or calls itself (kernels, exception handler, providers, commands, models, controllers, form requests, jobs, mailables, notifications, exceptions): subclassing those is where "trace everything" would start breaking applications; they are still traced line by line.

### D24 – Replay is the answer to "it already happened"
A trace cannot be recorded after the fact, and storing every request just in case is what the package refuses to do. So a request that already happened is *run again*: from a cURL command (what a browser or Postman can give you) or from a recorded trace. To make that safe it runs in a PHP process of its own, which also lets the code be compiled for line-by-line tracing from the first class; every database connection it touches is wrapped in a transaction that is rolled back; mail goes to the `array` mailer, queued jobs are dropped and broadcasts are not sent. Calls to other services cannot be undone, so replay is off in the `production` environment unless `replay.enabled` says otherwise. A POST gets a session token so CSRF does not refuse it; the user to act as is set on every guard, with no login.

### D25 – The tables create themselves
Asking for a migration, a publish and a config file before the first trace is the kind of step that makes people stop. The package ships its migration (so `php artisan migrate` includes it) and also creates the tables the first time a write fails because they are missing, using the same migration file, which does nothing when the tables exist.

### D26 – The config merges section by section, and exclusions add
Laravel's `mergeConfigFrom()` is shallow: a config file that mentions one key of a section replaces the whole section. For this package that meant that "add `admin/*` to the excluded paths" silently removed the login, webhook and queue-worker exclusions, and "mask `ssn`" removed the default masking keys: the opposite of what anybody means. `ConfigMerger` merges sections key by key; lists of things to leave out or mask add to the defaults (with `!entry` to take one away); lists that say what to look at (`code.paths`) replace them, because narrowing is the point. The dashboard's gate middleware is added to a configured middleware list if it is missing, so no config can open the dashboard by accident.

### D27 – The journal notes requests; it does not trace them
"Go back to a request that already happened" cannot work without something recorded at the time, and recording a full trace of everything is the cost the package refuses to impose. The journal is the smallest thing that makes the past reachable: a replayable description of each request (not a trace), kept for an hour. It is opt-in because it keeps request bodies, and it stores them masked, never raw: that keeps the rule that a secret never reaches the database, at the price that a masked field cannot be sent again. Raw-but-encrypted bodies were considered and refused for the same reason. A replay of a journal entry runs the request against the **current** code and data, which is what you want when debugging, and a thing to remember when comparing with what happened.

### D28 – The dashboard runs on a light web stack
The dashboard polls its API every few seconds, so whatever the application puts in its `web` group runs on every poll: permission syncs, "last seen" updates, locale, debug bars. In a real project that was 2.9 s per call (12 ms without), and a search or filter looked broken because the answer took seconds. The default stack keeps only what the dashboard needs, picked by class from the application's own `web` group at request time (so the application's `EncryptCookies` and `VerifyCsrfToken` subclasses are kept), and adds the gate. It is resolved at request time, not when the routes are registered, because the groups are not known yet in every context (`route:cache`, the console). Listing `'web'` in `dashboard.middleware` restores the old behaviour. A published asset copy wins only while it is not older than the package's own `dist/`, for the same reason: the dashboard that is served must be the one that is installed.

### D29 – Replay is simulation or real, and undo is a log of its own
A replay used to be one thing: roll everything back, let other side effects through. People want both "do not touch anything" and "do it, and let me take it back". They are different promises, so the person who replays chooses, and the dashboard says what each one does not cover.

*Simulation* keeps the transaction-and-rollback design (D24) and closes the cheap leaks inside the framework (notifications, the HTTP client, cache, session). It cannot close what is outside it, and the docs say so rather than call it "no effect at all".

*Real* cannot be rolled back with a transaction, because the changes must be visible and kept. Undoing from the trace was rejected: the trace masks secrets, cuts long values, leaves hidden attributes out, and a query-builder write has no "before". So a real run records an **undo log** of its own, from Eloquent model events, with the raw values: the one place the package keeps raw values, because an undo needs exact ones. That is why the log is encrypted with the application key, short-lived (`replay.undo_hours`), never returned by the API (counts only), and exists only for real runs. Statements the log has no exact copy of (query builder, raw SQL, pivot attaches) are counted per table and reported as not undoable; the log never claims more than it recorded.

Undoing is last-change-first inside one transaction per connection, and judges each row *as the later changes were just taken back*, so a row the replay itself changed twice is not a conflict. A row that someone else changed afterwards is. Without `force` any conflict cancels everything; with it the row is overwritten. Real runs are off by default in production and need an explicit confirmation in the dashboard and the API.

### D30 – The code of a step is shown from its own function outwards
A step's lines are stored by the innermost step that was open when they ran, so everything a controller action calls that is not a step itself (a constructor, a base class, a trait, a helper) is stored under the controller. Listing all of it, by file name, put the framework's hooks first and the action nowhere in sight. The view now starts from the step's own function and follows the calls written in it: a name in the text of a line that ran (`->charge(`, `Money::of(`, `new Money(`) links to a function that ran and has that name (and that class, when the call names one), and to a child step with that name. That is a heuristic on names, not a call graph, and it is stated as such: a candidate is linked once, at the first line that ran and calls it, and whatever no line calls goes into a closed "other code" section instead of being dropped, so nothing is lost and nothing is invented. A real call graph would need an entry and exit probe per function, which costs on every run for a view that is looked at rarely.

A controller that Laravel does not know as one (since Laravel 11 the base controller extends nothing) used to be proxied like a service, so its action was a `controller` step with a `service` copy below it, and the lines of the action were stored on the copy: the controller step owned only the constructor. The proxy now folds a call into the open `controller` step when the file and line are the same, and moves the arguments to that step's input. Older traces still contain the copy, so the code view uses a child step with the same file and line as the step's own code when the step has none.

The lines of a trace are numbers, and the files change while somebody is debugging them. Showing the current text under the old numbers puts every value on the line above (or below) its statement, which is worse than showing nothing. A probe already stores the first line of its statement as text, so the server can follow an edit without storing anything new: for each function it looks, nearest first, for the line that holds each probe's text and takes the most common offset (0 wins ties). It is a heuristic that only moves what it can match, a masked snippet is never matched, and when nothing matches it falls back to the recorded numbers and says so.

The output of a line moved to a pop-up for the same reason as everything here: the code is long, and a card under it is somewhere else on the screen when you need it.

### D31 – A fixed page with boxes that scroll
A debugging tool is used with the page open for a long time, on traces with thousands of steps. A page that grows with its content loses the header, the tabs and the list while you read, so the page is the window: the list, the steps and the details each scroll in their own box, and the figures above the flow fold away when the flow needs the room. Below 1280 px two columns do not fit, so the layout stacks and the pane scrolls as a whole, which is the only time the details are below the steps.

### D32 – The package has its own vendor and namespace
`your-vendor` and `RequestTracer\` were placeholders from the start (`Brand` is the one place that says so). The rename moves every class into `Ahmedhsieb\RequestTracer\`, including the strings that build or compare class names: the proxy namespace (`Ahmedhsieb\RequestTracer\Proxies`), the calls the Deep trace compiler writes into compiled code, and the Loader's and the proxy registry's "never trace the tracer" checks. Everything that is a user-facing name (the config file, `request-tracer:*`, the routes, the table prefix, the `X-Request-Tracer` header, the gate) is `Brand`'s and did not move, so an application changes only its composer requirement and the places where its own code names a class. Generated code (proxies, compiled files) calls classes by name, so the caches are keyed by the package version and the version was raised with the rename. A published config that names an old class is translated rather than refused, because that file is the one place an application is likely to have written such a name.
